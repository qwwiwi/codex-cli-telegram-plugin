# Known Codex CLI problems and how this bridge handles them

> **По-русски:** какие проблемы Codex CLI мешают работать с агентом через Telegram, что из них решает этот мост, что решает частично и что не решает и почему.

This page lists the problems people run into when they drive OpenAI Codex CLI from a chat, collected in November 2026 from the Codex documentation, other Telegram bridges for Codex and a reading of the code, and says for each one what this bridge does about it. File references point at this repository.

Status values: **solved**: the bridge removes the problem for its users; **partly**: the bridge lowers the risk or covers the common case, a gap remains; **not solved**: outside what a bridge can fix, or left as is on purpose.

| # | Problem | How this bridge handles it | Status | Why |
|---|---|---|---|---|
| 1 | Telegram is not an official Codex client; the official remote options drive Codex on your own desktop or in the cloud, not a CLI on your server | The whole bridge: it starts `codex app-server` next to your workspace and talks to it from a private Telegram chat (`plugin/src/codex/rpc.ts:37`) | solved | The bridge is the missing client for a CLI running on a server |
| 2 | Codex has no channel to push chat messages into a live session, so a chat bridge has nothing to plug into | A new message starts a turn; a message sent while Codex works is added to the running turn with `turn/steer` (`plugin/src/codex/session.ts:520`); `/stop` sends `turn/interrupt` (`plugin/src/codex/session.ts:560`) | solved | The app-server protocol gives the same result as a push channel |
| 3 | The standalone Codex MCP server mode was removed; integrations built on it stopped working | The bridge uses only `codex app-server` over stdio (`plugin/src/codex/rpc.ts:37`) | solved | It never depended on the removed mode |
| 4 | The one-shot `codex exec` mode has no approval buttons, and its behaviour when an action needs approval is undocumented | The bridge runs the long-lived app-server, which sends approval requests; they become Telegram cards (`plugin/src/codex/approvals.ts:35`) | solved | Approvals arrive as protocol requests the bridge can answer |
| 5 | Version confusion: posts quote CLI versions that do not exist, and no bridge states a minimum Codex version | `doctor` checks that `codex app-server` runs and that the CLI is logged in with ChatGPT (`plugin/scripts/doctor.ts:60`); the README asks to check `codex --version` | partly | The bridge uses recent experimental methods but declares and checks no minimum version, so an old CLI fails only at the first unknown method |
| 6 | The app-server interface is marked experimental and can change with any CLI update | The bridge opts into the experimental API explicitly (`plugin/src/codex/rpc.ts:80`); `update.sh` runs the full test suite and a build of a new bridge version in a separate folder before switching (`update.sh:72`) | partly | This guards bridge updates; a Codex CLI update the owner installs separately is not tested before use |
| 7 | Logging in with an API key is not supported; only a ChatGPT login works | The bridge refuses to start when the Codex account is not a ChatGPT login (`plugin/src/codex/session.ts:184`), and `doctor` reports it | not solved | The bridge is built around a personal ChatGPT plan and its rate limits; API-key accounts are out of scope for now |
| 8 | The Codex terms do not allow the app-server ChatGPT login for commercial or hosted services | The bridge serves exactly one owner on the owner's own server with the owner's own login (`plugin/src/codex/server.ts:105`) | not solved | This is a terms restriction, not a code problem; a paid hosted service for other people needs its own legal check |
| 9 | Approval cards are silently off when the approval setting is missing from a hand-written config | The installer always writes the approval mode (`install.sh:184`) and `doctor` prints the active mode: `never`, `standard` or `risky` (`plugin/scripts/doctor.ts:84`) | solved | The owner always sees which mode is on |
| 10 | An autonomous agent stalls on approval prompts nobody answers | A new install uses approval mode `never`: no cards of any kind, the agent never waits (`plugin/src/codex/approval-mode.ts:27`); `standard` and `risky` stay one flag away | solved | The owner chooses autonomy or confirmations at install time |
| 11 | A card appears only when Codex itself asks; anything the workspace sandbox allows, including deleting files inside the workspace, runs without a card | Codex runs in the `workspace-write` sandbox by default (`plugin/src/codex/session.ts:577`); the bridge state must live outside the workspace (`plugin/src/codex/server.ts:121`) | not solved | Codex decides what needs approval; a bridge cannot see an action the sandbox already allows. Keep the workspace under version control or backed up |
| 12 | There is no approve-for-the-whole-session button; a card waits 2 minutes, and long, secret-bearing or garbled requests are declined | One-time approvals by design: 2-minute timeout (`plugin/src/codex/approvals.ts:31`), automatic decline for requests over 3000 characters, with a secret or control characters, or beyond 4 open cards (`plugin/src/codex/approvals.ts:39`) | not solved | Kept on purpose: a session-wide approval would let later, different actions through. Use `risky` or `never` mode when cards come too often |
| 13 | Risky mode approves routine diagnostic commands with the bridge's own shell parser, which can misread a command | The parser accepts only known read-only commands (`plugin/src/codex/server-approval-policy.ts:150`) and asks for a card on dangerous ones (`plugin/src/codex/server-approval-policy.ts:156`); the mode is opt-in and covered by tests | partly | A hand-written shell parser can still miss an unusual form; it is off unless the owner picks `risky` |
| 14 | The GitHub connector can be set to skip approvals, so repository writes happen without a card | With cards on, connector write calls get a card that names the repository and branch (`plugin/src/codex/mcp-approval.ts:36`); skipping them is a setting in the owner's Codex profile that the installer never changes | partly | The bridge follows the owner's Codex profile; it cannot force a card the profile turned off |
| 15 | Running Codex as root through a relay needs passwordless sudo and gives Codex root rights | The bridge refuses to run as root (`plugin/src/codex/server.ts:93`), refuses the relay without approval cards (`plugin/src/codex/server.ts:225`) and without the sandbox (`plugin/src/codex/server.ts:229`) | partly | The relay stays optional and still carries root-level risk by design |
| 16 | A local task webhook lets other processes on the host submit work to the agent | The local listener binds to loopback only (`plugin/src/codex/external.ts:243`) and needs a bearer token; the inter-agent webhook never runs without a token or an IP allowlist (`plugin/src/codex/agent-webhook.ts:70`) | partly | Any process that holds the token can still submit tasks; keep the token private |
| 17 | Some chat bridges ship open defaults: an empty user list lets anyone in, and all tools are trusted | The bridge refuses to start unless exactly one owner and that owner's private chat are configured (`plugin/src/codex/server.ts:105`); the bot token and other secrets never reach Codex (`plugin/src/codex/environment.ts:3`) | solved | Access is closed by default |
| 18 | Codex works without a terminal screen, so there is nothing to mirror to see what it is doing | A live status line built from protocol events (`plugin/src/codex/work-status.ts:43`), an optional pinned HUD card with context and limits, and `/mirror` for work output (`plugin/src/codex/mirror.ts:15`) | solved | Protocol events replace the screen |
| 19 | Slash commands cannot be typed into a running session; each one is a separate protocol method | Bridge commands call the methods: `/compact` (`plugin/src/codex/session.ts:508`), model list in `/cc` (`plugin/src/codex/session.ts:300`), `/new`, `/stop` | partly | Only the commands the bridge maps are available from Telegram |
| 20 | Codex hooks use a different format from Claude Code hooks, so old permission rules do not carry over | An allow, confirm or deny classifier runs as a Codex `PreToolUse` hook (`plugin/scripts/codex-permission-hook.ts:11`); see `plugin/docs/claude-compatibility.md` | partly | Only the permission rules are ported; other old hooks are replaced by bridge features |
| 21 | Codex takes text and images only; voice messages need a separate transcription step | Voice messages are transcribed before they reach Codex (`plugin/src/telegram/media.ts:236`) when a transcription key is set | solved | Without the key the message reaches Codex marked as not transcribed, so Codex can ask for text |
| 22 | A request that was running when the process crashed is not repeated after a restart | Incoming messages wait in a queue on disk (`plugin/src/codex/inbox.ts:27`) and the thread ID is saved, so the dialogue resumes with `thread/resume` | partly | Queued messages survive; a turn cut off mid-way may need to be sent again |
| 23 | Codex can ask the user a question mid-task, and a chat bridge has to carry it | Codex questions become Telegram messages the owner answers (`plugin/src/codex/session.ts:825`) | solved | The protocol request is relayed both ways |
| 24 | One Codex session serves one person; there is no group or multi-chat mode | The bridge serves only the owner's private chat (`plugin/src/codex/server.ts:105`) | not solved | Kept on purpose: one owner, one private chat keeps approvals and data with one person |
